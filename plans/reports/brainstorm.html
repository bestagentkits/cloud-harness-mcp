Brainstorm Proposal: Third-Party Agent Toolkits

VERIFIED RECOMMENDATION (CANDIDATE E — 97/100) --ultra (best-of-5) --advice (Kongming)

Executive decision

Recommend Option A: a runner-mediated, content-addressed toolkit bundle cache with isolated provider adapters and read-only mount injection. Seed the cache for the three supported presets and bake only the pinned provisioning executables—such as the compatible ak binary—into a provisioner/executor image. Do not create a general plugin marketplace yet, and do not run toolkit installers in the long-lived executor.

This is the simplest viable direction that meets offline executor operation, dynamic selection, proprietary credentials, reproducibility, and existing skill provenance. It reuses CloudHarness’s current strengths: runner-side network helpers, owner-partitioned repository caching, encrypted secret references, a read-only executor root, and the built-in > owner > workspace > repository resolver.

Two core assumptions must be challenged explicitly:

  1. networkMode: "none" does not mean the whole workspace-open operation has zero network. CloudHarness already clones the target repository through short-lived runner helpers on bridge, while the executor itself stays on none. Toolkit acquisition should use that same disclosed boundary rather than silently enabling executor networking.
  2. Putting skill files on disk does not by itself mean a toolkit works. obra/superpowers requires session-start bootstrap/context activation; AgentKit emits target-specific content and configuration. Provisioning, discovery, and activation are separate contracts. CloudHarness can guarantee provisioning and its own skills_*/workspace_context surfaces, but cannot guarantee automatic bootstrap injection inside every arbitrary MCP client without a client-side integration.

1. Brainstorm Contract

Outcome

A caller can open a CloudHarness workspace with zero, one, or several approved or custom Git-based agent toolkits. The workspace reports the exact resolved toolkit versions/digests, exposes their normalized skills through skills_list, skills_read, skills_run, and workspace_context, and continues to run the executor with its requested network mode—normally none.

For the three presets:

  • mattpocock/skills: recursively normalize its categorized skills/<category>/<skill>/SKILL.md layout into CloudHarness’s skill view without running its installer.
  • obra/superpowers: mount its skills and expose its bootstrap/tool mapping through a CloudHarness context artifact. Full automatic activation is reported only for clients that implement the context-injection contract.
  • bestagentkits/agentkit: run a pinned, compatible ak CLI in a disposable provisioning helper, produce a normalized offline bundle, and consume AGENTKIT_API_KEY only through an owner-bound secret reference.

Two installation scopes are supported:

  • owner scope, default: selected for this workspace but surfaced at the owner provenance tier through a read-only off-repository mount; git status remains unchanged.
  • workspace scope, explicit opt-in: materializes approved toolkit output such as .cloud-harness/skills, .agentkit, CLAUDE.md, or AGENTS.md changes in the checkout; changes are previewed/reported and may intentionally dirty the repository.

Every active workspace is locked to immutable toolkit inputs. Recovery recreates the exact mount and configuration rather than resolving “latest” again.

Constraints

Security
  • Toolkit source URLs must reuse credential-free HTTPS, host allowlist, DNS/private-address rejection, and brokered-token model already used by repository cloning.
  • Custom toolkits are data/skill bundles, not arbitrary post-install command definitions. No upstream lifecycle hook, npm install, shell installer, Git hook, submodule, or LFS smudge process runs automatically during provisioning.
  • Toolkit scripts remain subject to explicit skills_run, exact bundle/script digest pinning, UID 10001 execution, dropped capabilities, read-only root, and workspace network policy.
  • Built-in skills remain highest precedence and cannot be overridden by owner-selected third-party content.
  • A selected upstream toolkit is not authored by CloudHarness. Preserve source: "owner" for precedence, but add origin metadata—toolkit ID, resolved commit/version, bundle digest, adapter version, and verification state—so owner-controlled is not mistaken for CloudHarness-reviewed code.
Network model
  • workspace_open.networkMode controls the long-lived executor only.
  • A short-lived runner provisioning helper may use operator-authorized egress, analogous to the existing clone/cache helper. This must be visible in preview/status/audit.
  • In operator cache-only mode, a cache miss fails deterministically with TOOLKIT_NOT_CACHED; it never turns on executor networking.
  • Cache-hit provisioning must work with the executor on none and with no external fetch from inside the executor.
Secret isolation
  • MCP/dashboard requests contain secret references only, never values.
  • AGENTKIT_API_KEY is decrypted by the runner immediately before provisioning, sent to the disposable helper through stdin into its process environment, redacted at the output boundary, and never placed in argv, Git, workspace files, Docker labels, cache keys, toolkit lock records, or audit details.
  • The helper uses tmpfs for HOME/XDG state and is removed on success or failure. Generated output is scanned for exact secret bytes before cache promotion.
  • Provisioning credentials are separate from runtime environment injection. Selecting AgentKit does not implicitly expose its API key to the long-lived executor.
  • Proprietary and private bundles are owner-partitioned and must not use cross-owner deduplication.
Provenance and non-destructive mounting
  • Preserve the current order: /opt/cloud-harness/skills built-in > /opt/cloud-harness/owner-skills owner > .cloud-harness/skills workspace > .agents/skills > .codex/skills > .claude/skills repository.
  • Owner toolkit projection is mounted read-only at /opt/cloud-harness/owner-skills and does not live under /workspace.
  • Workspace-scope materialization requires an explicit confirmation literal, is conflict-safe, and reports every path changed.
  • Same-name skills from different selected owner toolkits are deduplicated only when bundle digests are identical. A non-identical same-tier collision fails before executor creation and asks the caller to use include/exclude filters; array order must not become an accidental security precedence rule.
Compatibility
  • Absence of toolkits is fully backward compatible and produces current behavior.
  • Toolkit adapters declare compatible CloudHarness bundle format, provisioner/CLI version, client targets, and runtime executable requirements. A missing requirement fails as INCOMPATIBLE_TOOLKIT, not as a late shell error.
  • Open-source prompt/skill content may be portable, but automatic activation differs by MCP host. Compatibility must distinguish provisioned, discoverable, and auto-activated.
  • Toolkit updates do not alter an active workspace. New catalog pins apply only to new opens or an explicit future reopen/update operation.
Performance and idempotency
  • Cache key includes immutable source revision/digest, toolkit configuration, selected skills, adapter version, target, and relevant provisioner/CLI version—never a secret value.
  • Cache creation is single-flight, staged, validated, and atomically renamed to READY.
  • Workspace state persists both the normalized request fingerprint and resolved toolkit lock. Same idempotency key + same fingerprint returns the original result without refetch/reprovision; same key + different fingerprint returns CONFLICT.
  • Active workspace cache entries are lease-pinned and cannot be evicted.

Non-goals

  • A universal package manager or arbitrary executable plugin marketplace.
  • Automatically running third-party install scripts, hooks, telemetry, daemons, or package-manager lifecycle scripts during workspace_open.
  • Granting toolkit scripts runtime internet merely because the toolkit was fetched over runner-mediated egress.
  • Editing the user’s host/global Claude, Codex, Cursor, or shell configuration.
  • Guaranteeing automatic Superpowers/AgentKit prompt injection in MCP clients that do not consume the CloudHarness context contract.
  • Sharing proprietary/private toolkit output across owners.
  • Managing AgentKit billing, licenses, account creation, or revealing API keys.
  • Interactive setup during workspace_open; every required choice must be supplied in typed configuration or left for later explicit skill invocation.
  • Mutating or refreshing an active workspace when an upstream branch/tag moves.
  • Supporting arbitrary repo layouts or dependencies without a declarative custom-Git layout and compatibility check.

Acceptance criteria

  1. Schema/backward compatibility: contract tests accept omitted toolkits, [], one preset, multiple presets, and one custom Git source. They reject embedded Git credentials, non-HTTPS URLs, disallowed hosts, path traversal, duplicate instance IDs, unsupported per-preset config, and more than the configured selection cap.
  2. Offline executor: with all three preset bundles warm, workspace_open({networkMode:"none", ...}) succeeds; Docker inspection shows the executor on none; no fetch occurs in the executor; all selected skills are listable/readable.
  3. Cold-cache semantics: in cache-only runner mode an uncached selection returns TOOLKIT_NOT_CACHED and leaves no active executor or partial projection. In runner-egress mode only the ephemeral helper uses network and it is removed afterward.
  4. Secret non-disclosure: an AgentKit open using a stored AGENTKIT_API_KEY leaves no exact secret match in runner responses, logs, audit rows, workspace files, Git diff, toolkit locks, cache metadata, Docker inspect output for the executor, or retained helper state. The executor environment does not contain the key unless the user separately requested runtime environment injection.
  5. AgentKit reproducibility: the preset runs a pinned compatible ak version in a disposable home, resolves an exact kit version, records its output digest, and can recreate the workspace from cache with no network and no secret read.
  6. Provenance/precedence: a same-name fixture at all four tiers resolves built-in > owner > workspace > repository; skills_list/read reports toolkit origin and all shadowed candidates. Non-identical collisions between two owner toolkits fail rather than depending on request order.
  7. Non-destructive owner scope: baseline and post-open git status --porcelain are identical; owner toolkit mounts are read-only; attempts to modify them fail.
  8. Explicit workspace scope: no project file is written unless allowToolkitWorkspaceChanges: true is present. The result lists added/modified paths and digests. Reapplying an identical materialization is a no-op; an existing non-identical target fails without overwriting it.
  9. Toolkit-specific compatibility: Matt Pocock’s nested skills are normalized and discoverable; Superpowers’ using-superpowers bootstrap is returned by the context surface with client compatibility metadata; an AgentKit kit filtered with include/exclude selections exposes exactly the selected skills.
  10. Idempotency/recovery: repeated opens with the same key and fingerprint do not invoke a fetcher or CLI again. Recovery uses the stored immutable lock. Reusing the key with a different toolkit request returns CONFLICT.
  11. Atomic multi-toolkit behavior: if one of several requested toolkits fails resolution, validation, secret lookup, or compatibility, none is mounted and workspace creation fails cleanly.
  12. Dashboard/MCP UX: dashboard and MCP descriptions represent zero/one/many selections; show resolved source/version, cache state, activation level, repository changes, and provisioning-network disclosure; secret values never enter page state or request bodies.
  13. Performance SLOs [planning targets]: on the project benchmark host, a warm owner-scope bundle adds p95 ≤1 second for one toolkit and ≤2 seconds for three; no-toolkit opens regress by ≤250 ms or 5%, whichever is larger. Cold fetch time is bounded and reported but not assigned an upstream-dependent latency guarantee.
  14. Supply-chain bounds: archives/repos exceeding configured bytes, file count, depth, symlink policy, or extraction ratio fail before cache promotion. No .git/hooks, submodule, package lifecycle, or executable installer runs automatically.

2. Architecture and Design Options

Planning estimates below are directional, not delivery commitments.

Option A — Runner-side content-addressed cache and mount injection (recommended)

How it works:

  1. API validates a typed toolkit selection.
  2. Runner resolves catalog presets or approved Git refs to immutable revisions.
  3. On a cache miss, a short-lived constrained helper fetches or runs an approved adapter. AgentKit receives its key only in this helper.
  4. Adapter normalizes upstream assets into a CloudHarness bundle manifest: skills, references/scripts, bootstrap/context fragments, optional pinned CLI assets, dependencies, and provenance.
  5. Runner validates and atomically promotes the bundle into a CAS. Public bundles may be deployment-shared; private/proprietary bundles remain owner-scoped.
  6. Runner composes a workspace-specific read-only owner projection and optionally applies an explicitly approved project patch.
  7. Executor mounts the owner projection read-only, remains on the requested network mode, and the existing worker resolves normal skill precedence.

Primary assumption: The three supported toolkits can be normalized through bounded provider-specific adapters without requiring arbitrary upstream installer execution in the long-lived workspace.

First failure mode: An upstream toolkit changes layout/bootstrap/install semantics faster than its adapter/catalog pin is updated. The safe response is INCOMPATIBLE_TOOLKIT, not best-effort partial installation.

Pros: Reuses existing runner clone/cache, secret, helper, state, mount, and skill-resolution patterns; supports default-offline executors and dynamic combinations; keeps proprietary credentials/content owner-isolated; no per-toolkit executor image matrix; immutable locks make recovery and audit straightforward.

Cons: Requires three maintained adapters and a normalized bundle manifest; runner disk use grows with versions/config variants; Superpowers activation still needs a context/client contract beyond file mounting; cache GC, single-flight locking, and bundle validation are new operational concerns.

Quantified trade-offs [estimate]:

  • Initial build: roughly 3–5 engineer-weeks for contracts, cache/provisioning, three adapters, status/UI, and security tests.
  • New long-lived services: 0.
  • Warm overhead: approximately 0.2–1 second/toolkit; cold open: upstream-dependent 2–60 seconds.
  • Storage: typically 10–200 MB per normalized version/config; proprietary copies per owner.
  • Maintenance: medium—adapter updates when upstream contracts change.

Second-order effects: Immutable locks delay upstream security fixes until a new workspace/catalog pin is chosen; the dashboard must surface outdated/revoked pins. Disk GC becomes an availability concern and must respect active leases. Runner egress and executor egress become visibly distinct policy concepts.

Option B — Pre-baked image bundles with in-container CLI provisioning

How it works: Build executor variants containing open-source skill repos and the AgentKit CLI/content. workspace_open selects an image tag; startup copies or links requested assets into runtime roots. Missing AgentKit content is fetched by running ak kit init in the executor or must be baked during CI.

Primary assumption: Toolkit versions change slowly enough, licensing permits broad image distribution, and image rebuild/pull cost is preferable to runtime bundle resolution.

First failure mode: AgentKit content cannot legally or safely be baked into a generally available image, while fetching it in a networkMode:none executor is impossible. Enabling bridge for setup expands the executor’s secret/network blast radius.

Pros: Fastest steady-state setup after the exact image is local; very little runtime normalization logic; strong byte-for-byte reproducibility per image digest.

Cons: Image matrix grows combinatorially if combinations or versions get distinct tags; baking proprietary output risks cross-tenant disclosure and licensing violations; toolkit updates become image releases; image CVE patching and toolkit release cadence are coupled; a cache miss becomes an image pull, often slower than a small skill bundle; running ak in the long-lived executor risks secret/config leakage and violates the default network model.

Quantified trade-offs [estimate]: Initial build: 1–2 engineer-weeks for fixed presets, but ongoing CI/release overhead dominates; images: +0.3–2 GB depending on runtimes/content; three versions across three presets can create 9+ maintained artifacts before combinations; local image hit overhead: <0.5 seconds; cold registry pull: commonly 10–120 seconds; new long-lived services: 0, but more registry storage/build minutes; maintenance: high release coupling despite low runtime code.

Second-order effects: Frequent toolkit updates cause image churn, degraded node-cache hit rates, and larger rollback matrices. CVE remediation may unexpectedly upgrade toolkit content—or toolkit release urgency may force executor base-image churn. Proprietary revocation is difficult once layers are distributed.

Option C — Hybrid plugin/package-manager engine

How it works: Introduce a first-class toolkit registry and provider SDK. Providers resolve Git, OCI, npm, or proprietary registries; package manifests declare adapters, dependencies, hooks, bootstrap content, signatures, scopes, and secret slots. Runner installs signed packages into a shared CAS and invokes sandboxed provider plugins.

Primary assumption: CloudHarness is becoming a general toolkit marketplace with enough future providers to justify a provider ABI, registry governance, signing, and lifecycle model now.

First failure mode: The provider interface hardens before real upstream diversity is understood, creating an expensive abstraction that still needs special cases for AgentKit and Superpowers.

Pros: Best extensibility for future registries and toolkit types; strong place for signatures, SBOMs, compatibility metadata, revocation, and policy; shared CAS can minimize duplication for public content; cleaner future operator APIs for prewarm, inventory, and upgrades.

Cons: Largest security attack surface: executable provider code, manifest interpretation, registry trust, and migrations; considerably more public contracts and operational components than the three named toolkits require; harder to abandon once external providers depend on the ABI; delays delivering the requested presets.

Quantified trade-offs [estimate]: Initial build: 6–10+ engineer-weeks, plus registry/signing operations; new durable concepts: registry, provider ABI, package schema, signature/revocation policy, compatibility resolver, cache lifecycle; warm overhead: 0.5–2 seconds; cold: 3–60 seconds plus registry calls; storage efficiency: best for public packages; still owner-scoped for private/proprietary content; maintenance: high platform governance, lower marginal cost only after several additional providers.

Second-order effects: A “toolkit package” becomes an ecosystem compatibility promise. Revocation, malicious publisher response, semantic version resolution, provider sandboxing, and support policy become CloudHarness responsibilities. This shifts the product from workspace infrastructure toward marketplace governance.

3. Schema and API Design

Proposed workspace_open input

Use a strict discriminated union. Do not accept arbitrary shell commands or raw secret values.

type ToolkitScope = "owner" | "workspace";

type SkillFilter = {
  include?: string[]; // mutually exclusive with exclude
  exclude?: string[];
};

type SecretRef =
  | { scope: "global"; name: "AGENTKIT_API_KEY" }
  | { scope: "environment"; environmentId: `env_${string}`; name: "AGENTKIT_API_KEY" };

type ToolkitSelection =
  | {
      kind: "preset";
      instanceId?: string; // required only when selecting same preset with distinct configs
      id:
        | "mattpocock/skills"
        | "obra/superpowers"
        | "bestagentkits/agentkit";
      version?: string; // catalog version; omitted means catalog's pinned default, not arbitrary HEAD
      scope?: ToolkitScope; // default owner
      skills?: SkillFilter;
      activation?: "skills-only" | "toolkit-default";
      config?:
        | {
            kit: string;
            kitVersion?: string;
            target?: "portable" | "claude-code" | "codex";
            apiKey: SecretRef;
          } // valid only for bestagentkits/agentkit
        | {
            clientTargets?: Array<"claude" | "codex" | "cursor" | "all">;
          }; // only fields explicitly allowed by the chosen preset
    }
  | {
      kind: "git";
      instanceId: string;
      url: string; // credential-free HTTPS, allowlisted host
      ref?: string; // resolved once and locked to a commit
      subdirectory?: string;
      scope?: ToolkitScope;
      skills?: SkillFilter;
      layout?: {
        skillRoots: string[]; // bounded relative paths, no traversal
        recursive?: boolean;
      };
      activation?: "skills-only"; // custom Git cannot auto-inject bootstrap in the initial contract
    };

type WorkspaceOpenInput = {
  repositoryUrl: string;
  ref?: string;
  idempotencyKey: string;
  networkMode?: "none" | "bridge";
  environmentId?: string;                 // existing runtime environment semantics
  confirmEnvironmentInjection?: true;
  toolkits?: ToolkitSelection[];          // default [], max e.g. 8
  allowToolkitWorkspaceChanges?: true;    // required if any scope === workspace
  confirmToolkitSecretUse?: true;         // required when a toolkit has a SecretRef
};

Validation rules:

  • toolkits omitted and [] are identical.
  • Duplicate (id, instanceId) selections fail.
  • include and exclude cannot both be present.
  • workspace scope requires allowToolkitWorkspaceChanges: true.
  • Any provisioning secret reference requires confirmToolkitSecretUse: true; it does not require or imply confirmEnvironmentInjection.
  • AgentKit config is accepted only for the AgentKit preset; its API key name is fixed/allowlisted.
  • Custom Git accepts declarative roots only. It cannot specify install commands, environment variables, hooks, arbitrary adapters, or automatic bootstrap paths.
  • Operator policy may require custom refs to be full commit SHAs. When a branch/tag is accepted, the result always records the resolved commit.

Supporting APIs

A dashboard needs more than a blind workspace_open field. Add two bounded, read-only surfaces rather than embedding duplicate catalog logic in the frontend:

  • toolkits_list: preset IDs, display names, pinned/default versions, description/license/source, supported scopes/targets, required secret slots, activation level, cache availability, compatibility, and deprecation/revocation status.
  • toolkits_preview: validates selections against operator policy and returns prospective lock information available without mutation: cache hit/miss, required secret references, skill names/collisions, activation level, expected project target paths, and provisioning-network disclosure. It must not fetch uncached sources or expose secret values.

skills_list/read extends provenance with optional origin metadata:

origin?: {
  kind: "toolkit";
  instanceId: string;
  toolkitId: string;
  resolvedRevision?: string;
  bundleSha256: string;
  adapterVersion: number;
  verification: "built-in" | "catalog-pinned" | "custom-unverified";
};

This keeps the four precedence sources intact while exposing third-party lineage.

AgentKit secret and config handling

  • Keep AGENTKIT_API_KEY in the existing encrypted global/environment secret store. The fixed name is currently compatible with the secret-name policy.
  • Resolve only the referenced secret/version, not all environment secrets.
  • Seed the output redactor before invoking the helper.
  • Send the key over helper stdin; a rootless wrapper reads it, exports it only to the ak process, and runs with tmpfs HOME, .config, and .agentkit state.
  • Prefer current CLI capabilities such as a portable/build-only output into a staging mount. If an older supported CLI only provides --global, set its global home to a disposable staging directory, never the workspace or real owner home.
  • Cache the normalized kit output, not authenticated CLI state. The lock includes kit version, target, selected skills, adapter version, and ak version.
  • Mount any needed local-only ak binary read-only from an approved image/path. Do not download it at workspace startup.
  • If a later skill truly needs AgentKit network/API access at runtime, that is a separate explicit environment/network choice; the default provisioned toolkit must remain usable offline.

4. Recommended Direction

Why Option A wins

It is the only option that satisfies all named constraints without making CloudHarness either an image-distribution matrix or a premature marketplace platform. It aligns with current implementation evidence:

  • workspace_open already separates a bridge-connected clone/cache helper from the executor’s selected network mode.
  • The runner already has an owner-partitioned repository cache pattern and encrypted secret snapshots/redaction.
  • The executor already uses a read-only root, UID 10001, dropped capabilities, and writable host mounts.
  • The worker already knows /opt/cloud-harness/skills, /opt/cloud-harness/owner-skills, .cloud-harness/skills, and repository roots, with digest-pinned execution.
  • The current dashboard does not open workspaces—it explicitly tells users to open one from an MCP client—so dashboard workspace creation/preview is real new scope, not a small field addition.
  • Matt Pocock’s current repository has nested categorized skill roots, and Superpowers’ upstream porting guide says its bootstrap is required at session start. A normalization/activation layer is therefore necessary; raw repo mounting is insufficient.

The recommended design deliberately borrows only one idea from pre-baked images: seed popular preset bundles and pin the ak executable in deployment artifacts. The runtime source of truth remains the same normalized bundle/cache contract; there is no image-per-combination matrix.

Internal bundle contract

bundle/
  manifest.json
  skills/<normalized-name>/SKILL.md
  skills/<normalized-name>/references/...
  skills/<normalized-name>/scripts/...
  context/<client>/bootstrap.md        # approved presets only
  bin/...                              # approved, pinned optional assets

manifest.json records source/revision, bundle digest, adapter/provisioner versions, skill names/digests, context assets, runtime requirements, license/source metadata, and whether content is public or owner-confidential. It contains no credentials and no free-form lifecycle command.

  1. Repository URL and optional ref.
  2. Environment/runtime network settings.

  4. Review/preview.

Toolkit picker details

  • Human name and canonical ID.
  • Description, source, license, pinned version/commit.
  • Badges: Cached, Download on open, Credential required, Creates project files, Skills only, Context activation, Custom/unverified.

    • Mounted for this workspace — recommended; does not change repository (owner).

Decisions that must be resolved before implementation planning

  1. Client activation support: which MCP hosts will CloudHarness claim as auto-activated, and what exact session-start/context ingestion mechanism exists for each? Until proven, advertise only provisioning/discovery.
  2. AgentKit legal/cache policy: may normalized kit output be retained server-side, for how long, and must it be encrypted at rest beyond owner filesystem isolation?
  3. Operator egress policy: deployment-wide cache-only versus allowlisted runner fetch, and whether custom Git hosts can differ from repository hosts.
  4. Workspace-scope merge policy: recommended initial answer is fail on existing non-identical files; do not silently let upstream CLIs rewrite project instructions.
  5. Preset update policy: recommended initial answer is admin-reviewed catalog pins with revocation, not upstream latest at every open.

Final recommendation summary

Adopt the runner-mediated bundle cache and read-only injection design, with a small internal normalized bundle manifest and exactly three maintained preset adapters plus a declarative custom-Git adapter. Prewarm the named presets and pin provisioning tools, but avoid image variants and avoid a public provider/plugin ABI. Keep executor networking and provisioning egress as distinct, visible policies. Treat AgentKit credentials as one-shot provisioning inputs, not workspace environment defaults. Preserve the four-tier resolver and add immutable origin metadata. Default to a repository-clean owner mount; require explicit, previewed consent for project changes. Most importantly, do not claim that raw skill installation equals full toolkit activation—prove the bootstrap path per MCP client.

Supervisory Verdict: NO-GO to an immediate, execution-ready /ak:plan handoff; GO on Option A as the architectural direction.
Option A (runner-mediated immutable CAS + read-only owner mount) is sound and correctly chosen. However, implementation planning must not proceed as "ready to execute" until one P0 contract contradiction is corrected and external vendor feasibility is validated.

P0 Contract Contradiction & Correction: Secret Purpose Classification

The Contradiction: Candidate E's proposal states that AGENTKIT_API_KEY is strictly provisioning-only and denied from the executor container. However, the schema allows referencing a generic global secret: { scope: "global", name: "AGENTKIT_API_KEY" }.

In the current CloudHarness runner implementation (apps/runner/src/workspace-service.ts:626-655), all active global secrets are automatically decrypted and injected into every runtime executor container via hasActiveGlobalSecrets. A generic global secret reference would therefore silently leak the AgentKit API key into the runtime container's Config.Env (visible in docker inspect).

Required Data-Model Fix (P0 Invariant Before Planning)

Add an explicit secret purpose classification (e.g., purpose: "runtime" | "provisioning") to the CloudHarness secret store. Secrets marked purpose: "provisioning" are strictly excluded from global/environment runtime injection envelopes and workspace secret snapshots, and are accessible solely to ephemeral runner provisioning helpers.

Required Resolution of the 5 Feasibility Gates

  1. Client Activation Support: Default to orthogonal capability reporting (provisioned, discoverable, context-ready). Never label a generic MCP host auto-activated without a clean-session integration transcript proving context ingestion before the first agent action.
  2. AgentKit Legal & Offline Export Validation: Hard external gate. Validate vendor retention terms and run a live CLI export smoke test in disposable storage before planning AgentKit adapter implementation.
  3. Operator Egress Policy: Production deployments default to cache-only with prewarmed catalog bundles. Runner-mediated egress is an explicit operator setting, not user-escalated.
  4. Workspace-Scope Merge Policy: Adopt fail-on-existing non-identical target files. Require explicit confirmation literal (allowToolkitWorkspaceChanges: true) before mutating checkout files.
  5. Preset Update Policy: Use admin-reviewed immutable catalog pins. Normal pin updates affect new opens only; hard security revocations must actively block remounting/recovery of revoked bundle digests.
