engine, delivered on one branch. Phases 1 to 9 of
[`plans/260901-1255-skills-sh-and-skillx-compatibility/plan.md`](plans/260901-1255-skills-sh-and-skillx-compatibility/plan.md)

Closes #218.

## What this branch delivers

**Registry adapters and resolution.** `skills.sh` references resolve through GitHub with commit-OID
pinning; SkillX references go through its own adapter with an injectable transport. Acquisition lands
in the existing toolkit cache (one cache root, one projection path), toolkit bundles are now quarantined
when their bytes stop matching the recorded digest, and a deterministic 4-tier resolver
(`built-in > owner > workspace > repository`) owns the same-tier conflict rule for both the launch path
and the dashboard preview.

**Offline executor CLI.** `skills`, `skillx`, and an `npx` dispatcher ship in the image at
`/opt/harness/bin`, with npm left reachable at `/usr/local/bin/npx` so delegation cannot recurse. The
launchers read only the local catalog and projection, so they work with no network and fail closed with
`CACHE_MISS` plus the instruction that fixes it.

**Execution safety.** `skills_run` verifies the staged snapshot's digest before executing from it,
refuses a tree containing an escaping or broken symlink, answers `NO_EXECUTABLE_ASSETS` for an
instruction-only revision, and reports `executionMode` so a caller cannot read a stronger isolation
guarantee into a run than it had.

**Control plane and dashboard.** The skill registry (sources, revisions, sets, import jobs) is schema
v11 with composite owner foreign keys and an append-only revision trigger. Twenty-four internal
operations exist with strict schemas, dashboard projections, and a totality test that fails when an
operation has no mapper branch — it caught three registry operations nothing had accounted for. The
dashboard gained a Skills page (library, discovery, sets, registry), a reduced launch dialog with
skill-set selection and conflict resolution, and a TypeSafe panel.

**TypeSafe suggestions.** A dedicated integration credential (encrypted with the keyring envelope,
write-only, never a model provider), a bounded roster read from the workspace's own executor, an engine
whose redaction fails closed while suggestions fail open, and a `<skill_relevance>` block that carries
only a roster-validated identifier.

## Deferred, with the reason

Each of these needs a runner operation that does not exist, so the UI refuses the action rather than
appearing to offer it.

1. **Starting an import.** The wizard validates, reviews, and explains `CACHE_MISS`; its submit is
   unwired because the operation has no handler.
2. **Textual revision diff and fork.** Restore is implemented and produces a new immutable revision;
   diff and fork need operations the contract does not have.
3. **Registry entry actions.** The Registry tab reads cache state, pinned commit, skill count, and lock
   state; enable, disable, and pin need a handler.
4. **Editing an existing skill's instructions.** `skill_update` takes metadata only, so the editor
   creates skills.
5. **Federated search.** Search covers the local registry; the provider fan-out depends on the
   unverified SkillX search API.
6. **Helper-container execution.** Skill scripts run as a local child process under UID 10001 from the
   verified read-only snapshot, and the response says `executionMode: 'local'`. The
   `runPrivilegedEphemeralExec` path is gated on an owner privilege grant, and making that grant
   mandatory would turn a hardening step into a launch blocker.

The automated lens reports eight findings in `apps/runner/src/state-store.ts`: one `as unknown as` cast
on the legacy `networkMode` field and three `JSON.parse(row.provenance_json)` calls in the legacy
provenance readers. They predate this work and sit outside every region this branch changes. The same
applies to the unused `record` parameter in `applyWorkspaceToolkitPatches`. They are listed here so a
reviewer sees them rather than discovering them.
